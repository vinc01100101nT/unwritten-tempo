The Unity 2D game is named **unwritten** (all lowercase) — the real game, a separate project/folder from this React prototype repo (see [[unity-2d-direction]]).

**Direction (decided 2026-06-13):** build the playable world FIRST, then the UI shell, then graft on the skill system. Order: art → animated characters → tilemap world → towns/fields/maps → NPCs/interaction → monsters → UI toggle panels (today's windows: [[hud-progression-windows]]). The graph-based skill-draft system (issues VIN-3…VIN-7) is DEFERRED — it slots into the Skills panel later.

**Why:** the user chose a "real game you can walk around in" before the unique mechanic, reversing the original slice plan (which deferred art/maps to prove the skill-draft hook fast).

**Art:** Ninja Adventure pack (pixel-boy, **CC0**) is the base — top-down 8-way, 16×16 tiles → import at **PPU 16, Point filter**. LPC generator (CC-BY-SA/GPL) reserved for equipment-on-character later.

Workflow: scripts are authored in this repo's `unity/Assets/Scripts/` then COPIED into the project's `Assets/Scripts/`; art/asset packs belong ONLY in the project's `Assets/`, never in this prototype repo. **Phase F fixes (2026-06-14, after first Play test):** (1) **Equipping gear changed nothing** — root cause was STALE DATA, not wiring: the `Item` .assets were created in Phase E before the stat fields existed, and `ItemStarterSet.EnsureStarterItems` was idempotent (`if asset exists → continue`), so re-running "Create Starter Items" never wrote the new +ATK/+HP onto existing assets (all bonuses stayed 0). **Fix:** EnsureStarterItems now LOADS the existing asset and re-applies displayName/slot/icon/bonuses + `EditorUtility.SetDirty` (creates only if missing) → re-running updates in place. **Lesson:** any idempotent asset generator that gains new fields must update-in-place, not skip-if-exists, or old assets silently keep defaults. **Attack animation (2026-06-14):** player looked static when attacking (built from the WALK sheet only). The pack HAS attack art: each character `Actor/Character/<Name>/SeparateAnim/Attack.png` = **64×16 = 4-column Down/Up/Left/Right attack POSE strip** (1 frame per direction; SeparateAnim also has Walk 64×64/Idle/Jump/Dead/Item/Special1-2), and animated slash sheets in `FX/Attack/<Name>/SpriteSheet.png` (mostly **128×32 = 4 frames of 32×32**; chose **SlashCurved**) + `FX/Slash/*` (non-uniform widths — avoid). **No multi-frame character swing**, so: (a) `CharacterAnimator2D` gained `attackSheet` (Texture2D) → builds 4 pose sprites at Awake via `Sprite.Create` (rect per 16px col, pivot centre, ppu=16 to match walk) + `PlayAttack(dir, hold)` which snaps facing to the target and shows the pose for `hold`s, overriding walk; (b) new `SlashEffect.cs` slices a sheet's frames at runtime (`Sprite.Create` per 32px frame, no asset-slicing) and plays once then self-destroys (sortingOrder 40); (c) `PlayerAttacker` each swing calls `anim.PlayAttack(dirToTarget, 0.18)` + `SlashEffect.Spawn(slashSheet,32,4,22fps, targetPos, 1.1)` (captures target pos BEFORE TakeDamage may destroy it). KEY trick: `Sprite.Create` from an imported Texture2D at runtime needs NO Read/Write and NO pre-slicing — used for both the attack poses and slash frames.
